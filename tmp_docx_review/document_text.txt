5.7.1  System Interfaces & APIs â€” Frontend
The Bloom frontend communicates with backend services exclusively through asynchronous JavaScript API calls. No synchronous XMLHttpRequest calls are used; all network operations return Promises or use async/await, ensuring the UI thread remains responsive during data fetching.

All authentication operations are routed through the Firebase Authentication SDK:
firebase.auth().createUserWithEmailAndPassword(email, password) â€” called on the registration form submit. On success, a new Firestore users document is created with the returned uid.
firebase.auth().signInWithEmailAndPassword(email, password) â€” called on the login form submit. On failure, the SDK returns an error code (e.g., auth/wrong-password) that is mapped to a user-friendly message.
firebase.auth().onAuthStateChanged(callback) â€” registered on every protected page. The callback is fired once on page load with either a User object (authenticated) or null (unauthenticated).

Cycle logs are stored in and retrieved from the cycleLogs Firestore collection:
Fetching: db.collection('cycleLogs').where('uid', '==', currentUser.uid).orderBy('date', 'desc').get() retrieves all logs for the authenticated user, sorted most-recent-first.

8.1  Frontend Implementation
The Bloom frontend implementation translates the design system and component architecture into a functioning, production-ready user interface. This section documents the key implemented features, the event-driven interaction model, and the techniques used to keep the UI performant and maintainable.
Dynamic Dashboard
On authenticated page load, the Dashboard executes a Promise.all() that simultaneously fetches the user profile, the most recent 12 cycle logs, and the userâ€™s goal from Firestore. Once all three requests resolve, the Dashboard renders synchronously from the fetched data:
The Cycle Snapshot Cardâ€™s progress ring SVG stroke-dashoffset is set proportionally to the ratio of elapsed cycle days to average cycle length.
Phase colour classes (phase-menstruation, phase-follicular, phase-ovulation, phase-luteal) are applied to the Cycle Phase Card container, changing its border and background tint.
Trend charts are drawn by passing the cycle log array to a buildCharts(logs) helper that extracts the relevant metric time series and invokes Chart.js.
A Firestore onSnapshot listener is registered after the initial render, so any new log added from the Calendar page is automatically reflected on the Dashboard within milliseconds.
Interactive Calendar with Prediction Overlays
The calendar grid is generated by a buildCalendar(year, month) function that creates a 2D array of date objects and renders them as a table of <div> cells. Overlay application works in three passes:
Historical pass: Each cycle log document is checked against the cellâ€™s date. If a log exists for that date with non-zero flow, the cell receives the period-day class.
Prediction pass: The rolling average cycle length is used to project the next 3 period start dates and their durations. Projected period cells receive the predicted-period class (lighter shade) to visually distinguish predictions from confirmed logs.
Fertile/ovulation pass: Ovulation is estimated as 14 days before the next predicted period. The 5-day fertile window centred on ovulation day receives the fertile-window class.
Month navigation calls buildCalendar() with the new month parameters and re-applies all three overlay passes against the same data, which is cached from the initial fetch.
Cycle Logging System
The Cycle Log Modal is built as a self-contained component with its own state object (currentLog) that accumulates field values as the user interacts:
Chip selections toggle their active state and push/pop values from currentLog.symptoms[].
Slider inputs update currentLog.sleep, currentLog.stress, or currentLog.activity on every input event, providing live numeric feedback.
On submit, the component validates that flow intensity is selected (the only required field), then calls db.collection('cycleLogs').set(currentLog, { merge: true }) with the date as the document ID.
A loading spinner replaces the submit button during the async write, and a success toast notification is shown on resolution.
Educational Resource Browsing
The Resource Centre uses a virtualised rendering approach for performance: only the cards currently visible in the viewport (plus a small buffer above and below) are fully rendered. As the user scrolls, off-screen cards are replaced with lightweight placeholder divs of the same height. This technique ensures smooth scrolling even with a large resource catalogue.
Clinic Finder with Map Integration
The Clinic Finder feature is initialised in three sequential steps to prevent map rendering errors:
Data load: All clinic documents are fetched from Firestore and stored in a local clinics[] array.
Map initialisation: Leaflet.map() is called on a <div id="map"> container only after the DOM has fully rendered (deferred via requestAnimationFrame to avoid the Leaflet â€œmap container not foundâ€ error common when initialising inside conditionally rendered elements).
Marker placement: Clinic coordinates are iterated and L.marker([lat, lng]).addTo(map) is called for each, grouping markers into a cluster layer.
Filter and search operations update the clinics displayed by hiding/showing markers on the map (via layer.setStyle or addTo/removeFrom the cluster group) and re-rendering the card list from the filtered array.

9.1  Early Design â€” Wireframes
The initial design phase focused on information architecture and navigation structure before any visual styling decisions were made. Wireframes were produced as low-fidelity greyscale sketches for each of the four main screens.
Dashboard wireframe: Explored different card arrangements for the cycle summary. All wireframes were reviewed against the following principles: simple navigation structure, clear separation of features, and minimal visual clutter. Only elements that directly served a user task were included.
9.2  Design Iterations
Moving from wireframes to interactive prototypes, several significant design decisions were revised based on feedback:
Card-based layout adoption: The table-heavy early designs were replaced with a fully card-based layout across the Dashboard, Resources, and Clinic Finder. Cards proved more scannable and more naturally responsive on mobile.
Phase colour coding: The first prototype used a single pink accent for all cycle phases. Feedback highlighted that this made it impossible to distinguish phases at a glance on the calendar. Four distinct colours were introduced: deep red for menstruation, lavender for the follicular phase, green for ovulation, and warm amber for the luteal phase. Each colour was also assigned a text label and icon to support colour-blind users.
Cycle Log Modal redesign: The first version of the log form was a full page. Users found switching between the calendar and the log page disruptive. Moving the form into a modal overlay that slides up over the calendar solved this and was universally preferred in peer reviews.
Spacing and readability: Early prototypes had insufficient white space between UI elements, making the interface feel cramped. A 4 px base spacing scale was introduced and consistently applied, improving readability significantly, particularly on smaller screens.
Filter UX for the Clinic Finder: The original filter design used a sidebar panel that had to be explicitly opened. This was replaced with always-visible dropdown controls above the map, reducing the interaction cost of filtering from two taps to one.
9.3  Final UI Decisions
The final production design locked in the following key decisions:
Bloom Pink branding: The primary colour #C2187A was selected as the definitive Bloom brand colour after comparing multiple pink hues against accessibility contrast requirements. It achieves the required 4.5:1 contrast ratio against white at all text sizes.
Rounded component language: 8 px border-radius on cards and buttons, 16 px on modals. This softens the interface and communicates safety and approachability, which is especially important for a health application that may surface sensitive information.
Typography: Arial was selected as the primary typeface for its universal availability across operating systems, high legibility at small sizes, and neutral, professional character. Heading weights (700) create clear visual hierarchy without requiring a decorative display font.
Icon system: A consistent icon set (Heroicons outline style) is used for navigation items, action buttons, and category labels. Icons are always accompanied by a text label (never icon-only) on primary navigation elements, supporting users who cannot readily identify icons.
Micro-interactions: Subtle hover lifts (box-shadow increase + translateY(-2px)) on cards, smooth modal transitions (300 ms ease-out), and loading spinners on async actions were retained from the prototype stage as they significantly improved the perceived responsiveness of the application.
